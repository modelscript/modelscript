# ModelScript Agent Guidelines

## Terminal Workaround (Linux)

**IMPORTANT:** On this system, `node -e` with multi-line inline scripts causes the terminal to hang indefinitely even after the command finishes. This is a known Antigravity bug on Linux.

**Rules:**

1. **Never** use `node -e "..."` with multi-line JavaScript/TypeScript.
2. Instead, write the script to a scratch file inside the repository workspace and run it:
   ```bash
   cat > languages/modelica/tests/scratch.ts << 'EOF'
   // your code here
   EOF
   npx tsx languages/modelica/tests/scratch.ts
   ```
3. For simple one-liners, prefer `npm run test` or package scripts.
4. Always set `WaitMsBeforeAsync` appropriately — use short timeouts (500-2000ms) for commands that might hang, and inspect background tasks using `manage_task(Action: 'status')` or wait for reactive task completion notifications.
5. **Build commands** (`npm run build`, `nx run`, etc.) hang indefinitely when there are lint or compilation errors. Always use a short `WaitMsBeforeAsync` (e.g., 500ms) or pipe through `timeout 30` to force termination.
6. **Task cancellation & output inspection:** If a command times out or is canceled, check its task status and output log via `manage_task(Action: 'status', TaskId: ...)`. A terminated command may have produced useful compiler errors before being killed.
7. **Apparent hangs:** When a command appears to hang (stuck in RUNNING with no output), **always assume it is the known Antigravity Linux terminal bug first**, not an infinite loop in the code. Inspect the task's output before assuming code bugs or killing prematurely.
8. **Test script placement:** Never place test scripts that import project modules in `/tmp/`. Scripts in `/tmp/` cannot resolve monorepo workspace imports or relative paths back into the repo, and writing to `/tmp` violates workspace boundaries. Always place ad-hoc test scripts inside the workspace (e.g., `languages/modelica/tests/` or a scratch file alongside the source).
9. **WASM Parser:** The project uses a custom, native WebAssembly GLR parser (`parser.wasm`) generated by `@modelscript/dsl`'s compiler (`buildParser`). Never import or reference `tree-sitter`. The parser is initialized via `createWasmParser`:
   ```typescript
   import { createWasmParser } from "@modelscript/modelica/parser";
   import { Context } from "./src/context.js";
   const modelicaWasmPath = require.resolve("@modelscript/modelica/parser.wasm");
   const { parser } = await createWasmParser(modelicaWasmPath);
   Context.registerParser(".mo", parser);
   ```

## Linear Memory & Data-Oriented Architecture

**IMPORTANT:** The compiler operates on a data-oriented struct-of-arrays architecture in WebAssembly linear memory (`DAEBuilder`, linear CST pointers). Never instantiate heavy AST wrapper objects for expressions or flattening logic.

**Rules:**

1. **Direct lowering to DAE arena:** Equations, expressions, and statements are lowered directly from linear memory parser nodes into `DAEBuilder` integer IDs (`ExprId`, `EqId`, `StmtId`).
2. **Zero intermediate wrapper allocations:** Do not construct intermediate TypeScript AST wrapper classes.
3. In the arena-native pipeline (`ModelicaFlattener`), CST nodes are accessed via `db.cstNode(classId)` and lowered directly into `DAEBuilder`.

## Compilation Pipeline Architecture

There is a single canonical flattening pipeline in the codebase: the arena-native pipeline (`Context.flattenArena()` → `ModelicaFlattener` → `DAEBuilder`).

### Pipeline Stages

```
Source (.mo) → WASM GLR Parser → Linear Memory CST
    → SymbolIndexer → SymbolIndex (flat symbol table)
    → WorkspaceIndex → Unified SymbolIndex (multi-file)
    → QueryEngine (Salsa memoization)
    → Linting (CompilerLint / CodeGraph & lint__ query hooks)
    → ModelicaFlattener (AssemblyScript WASM Kernel / TS Bridge) → DAEBuilder
    → BLT / Solvers / Simulation
```

### Polyglot Languages (`languages/`)

ModelScript is a polyglot compiler supporting multiple engineering domains with unified querying and cross-language interoperability:

- `languages/modelica/`: Modelica 3.x simulation and physical modeling
- `languages/sysml2/`: SysML v2 AST querying, KerML standard library snapshot, and verification
- `languages/step/`: STEP (ISO 10303) grammar and querying for CAD/CAE interoperability
- `languages/owl2/`: OWL2 Functional Syntax parsing and ontological knowledge extraction
- `languages/csv/`: CSV tabular data parsing and validation
- `languages/cfd/`: CFD mesh & SU2 dialect support
- `languages/fea/`: Finite element analysis configuration
- `languages/scad/`: OpenSCAD language support and CSG evaluator
- `languages/ssp/`: System Structure and Parameterization definitions

### SymbolIndex Data Model

The `SymbolIndexer` walks the CST and produces a flat `SymbolIndex`:

- `symbols: Map<SymbolId, SymbolEntry>` — all indexed declarations
- `byName: Map<string, SymbolId[]>` — name-based lookup
- `childrenOf: Map<SymbolId | null, SymbolId[]>` — parent→children tree

Each `SymbolEntry` stores `startByte`/`endByte` ranges back into the source, allowing CST recovery via `db.cstNodeRange()`.

**What is indexed:** class definitions, component declarations, extends clauses, connect equations, function definitions.

**What is NOT indexed:** equations, algorithm statements, expression bodies, annotations. These exist only as CST nodes within the class body and are lowered directly during flattening.

### QueryEngine (Salsa)

The `QueryEngine` wraps the `SymbolIndex` with memoized queries. Key queries:

| Query                   | Purpose                                                           |
| ----------------------- | ----------------------------------------------------------------- |
| `instantiate`           | Resolve all elements of a class (components + inherited)          |
| `classInstance`         | Resolve a component's type to a specialized class ID              |
| `resolveSimpleName`     | Scope-based name resolution                                       |
| `variability`           | Determine parameter/continuous/discrete/constant                  |
| `causality`             | Determine input/output/local                                      |
| `effectiveModification` | Resolve merged class modifications across inheritance hierarchies |

**Salsa algorithm:** `fetch → deep_verify → execute → backdate`. Query results are cached and invalidated only when their transitive dependencies change.

**AST wrapper nodes are NOT stored in Salsa.** The Salsa cache stores semantic query results (types, variabilities, resolved element lists). CST nodes are retrieved on-the-fly via `db.cstNode(symbolId)`.

### ModelicaFlattener

Located at `languages/modelica/src/flattener.ts` (coordinated with `languages/modelica/assembly/flattener.ts`).

Supports backends: `"wasm" | "hybrid" | "ts" | "diff"` (defaults to `"hybrid"`).

**Two-layer architecture:**

- **Layer 1 (Components & Hierarchy):** Reads Salsa queries (`instantiate`, `classInstance`, `resolveSimpleName`, `variability`) to emit variables and parameters into `DAEBuilder`.
- **Layer 2 (Equations & Algorithms):** Retrieves CST sections via `db.cstNode(classId)`, iterates equations and statements directly using linear memory accessors (`Cst`), and compiles expressions into arena expression IDs.

**Lowering Rules:**

1. **Real coercion in binary expressions:** If one operand of a binary operator is Real-typed and the other is Integer, the Integer operand is cast to Real via `castToRealExpr()`.
2. **Negation distribution:** `-(a * b)` is rewritten to `(-a) * b` to match OpenModelica's canonical form.
3. **Real coercion in bindings:** When a `VarType.Real` variable has a binding expression, `castToRealExpr()` is applied to convert integer literals to real (e.g., `parameter Real R = 100` → `parameter Real R = 100.0`).
4. **Literal kind for bindings:** When a literal binding is set, check `varType` — use `addIntLiteral()` for `VarType.Integer`, `addRealLiteral()` for `VarType.Real`.

### DAEBuilder

Located at `packages/runtime/src/dae/wasm_dae.ts` (exported via `@modelscript/runtime`). A **data-oriented** (struct-of-arrays) container in linear memory:

- `varData` — variable metadata (name, type, variability, causality, start, flags)
- `exprData` — expression tree (kind, data1, left, right)
- `eqData` — equations (kind, lhs, rhs, flags)

Post-processing steps after flattening: constant folding (`foldArenaConstants`) → alias elimination (`eliminateArenaAliases`) → BLT transformation → simulation.

## Linter Rules

When adding new linter rules to `@modelscript/modelica`, follow this pattern:

### 1. Define the Error Code

Add a new entry to `ModelicaErrorCode` in `languages/modelica/src/errors.ts`:

```typescript
RULE_NAME: {
  code: XXXX,          // Unique numeric code (see numbering scheme below)
  rule: "rule-name",   // Kebab-case identifier
  severity: "error",   // "error" | "warning" | "info"
  message: (param: string) => `Descriptive message with '${param}'.`,
},
```

**Linter Text Generation Rules:**

1. **Match OpenModelica:** Error messages must exactly match or closely mirror OpenModelica's diagnostic messages whenever possible.
2. **Quote Identifiers:** Always wrap variable names, class names, and evaluated expressions in single quotes (e.g., `'${componentName}'`).
3. **Punctuation:** End the diagnostic message with a period (`.`).
4. **Descriptive Parameters:** Use clear, descriptive string parameter names (e.g., `className: string`, `actualType: string`) in the `message` function signature.
5. **Multi-line Formatting:** If the error message requires showing complex types or signatures, use template literals with actual newlines and indentation (e.g., `\n  ${typeSignature}`).

**Error code numbering:**

- `1xxx` — Parser / Syntax
- `2xxx` — Name resolution
- `3xxx` — Type checking
- `4xxx` — Structural / Semantic
- `5xxx` — Equations & Algorithms

### 2. Implement the Lint Rule

Lints in ModelScript are implemented in one of two ways:

#### A. CST Lints (`CompilerLint`)

For syntax and local semantic checks, define a `CompilerLint` in the appropriate module under `languages/modelica/src/lints/` (e.g., `syntax-placement.ts`, `types-expressions.ts`, `hierarchy-variability.ts`, `connections-streams.ts`, `synchronous-clocks.ts`, `cfa.ts`):

```typescript
import type { CodeGraph, CompilerLint, u32 } from "@modelscript/dsl";
import { ModelicaErrorCode } from "../errors.js";

export const modelicaSyntaxLints: Record<string, CompilerLint> = {
  ruleName: {
    nodes: ["target_node_kind"],
    severity: ModelicaErrorCode.RULE_NAME.severity,
    code: ModelicaErrorCode.RULE_NAME.code,
    message: (target) => ModelicaErrorCode.RULE_NAME.message(target.text),
    query: (db: CodeGraph, node: u32) => {
      // Linear CST inspection using db.ast and db.scope
      if (/* condition */) {
        db.diagnostic(node);
      }
    },
  },
};
```

Export the rule in `languages/modelica/src/lints/index.ts` so it is included in `allModelicaLints`.

#### B. Semantic / Salsa Query Lints

For inter-procedural checks or checks requiring global symbol table resolution, implement a `lint__<ruleName>` query hook in `languages/modelica/src/queries.ts` attached to the relevant symbol type (`classDefinitionQueries`, `componentDeclarationQueries`, etc.).

### 3. Add a Test Case

Create a `.mo` file in the appropriate `testsuite/OpenModelica/flattening/` subdirectory.

- For **correct** tests (`// status: correct`): the `// Result:` block contains the expected flattened output.
- For **incorrect** tests (`// status: incorrect`): the `// Result:` block contains the expected diagnostic output in the format:
  ```
  // [relative/path/to/file.mo:startLine:startCol-endLine:endCol] Severity: [MXXXX] Message text.
  ```

### 4. Verify

```bash
npm run build --workspace=@modelscript/modelica      # Compile + lint
npm run test:unit --workspace=@modelscript/modelica # Run unit tests
npm run test:omc --workspace=@modelscript/modelica  # Run OpenModelica testsuite
```

## Test Runner

**IMPORTANT:** The testsuite runner for `@modelscript/modelica` is located at `languages/modelica/tests/testsuite-runner.ts`. It does **not** support `--filter`. Arguments are subdirectory names or `.mo` file paths relative to `languages/modelica/testsuite/` or the current working directory.

**Run commands:**

```bash
# Run unit tests only
npm run test:unit --workspace=@modelscript/modelica

# Run OpenModelica testsuite (all tests)
npm run test:omc --workspace=@modelscript/modelica

# Run full test suite (unit + OpenModelica testsuite)
npm run test:full --workspace=@modelscript/modelica

# From repo root: run a specific test suite subdirectory
npm run test:modelica -- OpenModelica/flattening/modelica/types

# From repo root: run a single test file
npm run test:single -- OpenModelica/flattening/modelica/types/IntegerToEnumeration.mo

# From repo root: update expected output against OpenModelica ground truth
npm run test:modelica:update -- OpenModelica/flattening/modelica/types/IntegerToEnumeration.mo
```

**Runner Flags:**

- `--omc`: Invokes local OpenModelica (`omc`) directly to generate ground-truth instantiation and simulation results.
- `--update`: Auto-rewrites the `// Result:` block in `.mo` files. **Always use `--update --omc` together** when updating test baselines to ensure ModelScript bugs are not accidentally recorded as expected results.
- `--flattener=hybrid|wasm|ts|diff`: Sets the flattener backend (default: `hybrid`).
- `--concurrency=N`: Number of parallel worker processes (default: calculated based on available CPU/memory).
- `--fresh-process`: Spawns isolated worker processes per test rather than using the persistent pool.
- `--mark-xfail`: Automatically toggles `// xfail: true` annotations based on current test passes/failures.
- `--allow-failures`: Exits with code 0 even if some tests fail.

**Rules:**

1. **Never** use `--filter` — it does not exist and the argument will be interpreted as a path.
2. Pipe through `timeout 60` if running directly with `npx tsx` to guard against terminal hangs.

## Linter and Flattener Synchronization

**IMPORTANT:** The linter and the flattener must always be in sync. Do not move diagnostics or features from the linter to the flattener (or vice versa) simply to work around implementation difficulties.

**Rules:**

1. **Keep diagnostics where they belong:** If a diagnostic is implemented as a linter rule in ModelScript (analogous to OMC's frontend semantic checks), it must remain in the linter.
2. **Fix the root cause:** If the linter lacks context that the flattener has (e.g., proper state management or hierarchy traversal), fix the linter's implementation rather than moving the check to the flattener.

## Test Diagnostic Messages and Line Ranges

**IMPORTANT:** When a test fails because of a diagnostic mismatch, always fix the **code** to produce the same error message as OpenModelica. The `.mo` test expected output reflects the correct OMC behavior and should be treated as the source of truth for error messages.

**Rules:**

1. If a test fails because the **error message text** differs from the expected output, **update the error message in the ModelScript code** (e.g., in `languages/modelica/src/errors.ts` or `src/flattener.ts`) to match OpenModelica's format.
2. If a test fails only because of a **line/column range** mismatch in the diagnostic output, **update the `.mo` test file's expected `// Result:` block** using `--update --omc` or manual adjustment — only when it is difficult to make ModelScript produce the exact same ranges.

## Component Ordering in Tests

**IMPORTANT:** Do not reorder components (variables, protected declarations, etc.) in `.mo` test expected output to match ModelScript's current ordering. The expected output reflects the correct ordering from OpenModelica.

**Rules:**

1. If a test fails only because components appear in a different order, **fix the flattener/DAE printer** to emit components in the correct order, matching the test's expected output.
2. **Never** swap, reorder, or rearrange component declarations in test `// Result:` blocks to work around ordering bugs in the flattener.

## Git Commits

**IMPORTANT:** Never run the `git commit` command yourself. The user will handle committing the code.

When generating git commit messages (including via the "generate git commit" button), always use **Conventional Commits** format:

**Rules:**

1. **Never run `git commit`**. Always let the user run the commit command.
2. **Never commit and/or push changes without explicit authorization.**
3. **Auto-generate commit messages.** After every successful fix or change, proactively generate a commit message without being asked.
4. **Use conventional commit format** — `type: description`.
5. **Valid types:** `feat`, `fix`, `refactor`, `chore`, `docs`, `build`, `ci`, `perf`, `test`, `style`.
6. **All lowercase** — no capitalization in description, no title case.
7. **No trailing period** — the message is a phrase, not a sentence.
8. **Use scope when relevant** — `type(scope): description`, e.g. `fix(core): ...`, `feat(cli): ...`.
9. **Comma-separated list for multiple changes in description** — group related changes.
10. **Be terse but descriptive** — describe _what_ changed, not _why_.

**Examples:**

```
fix(core): nested array toJSON serialization, refactor annotation clause merging
feat(cli): add partial function application support
fix: 2D array equations, refactor built-in function dispatch to metadata-driven tables
ci: add gpg commit signing to release workflow for verified commits
chore: use wildcard dependency ranges for internal workspace packages
docs: add security policy and vulnerability reporting guidelines
```
